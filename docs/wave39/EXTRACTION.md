# Wave39 — reconsidering departure

The eight-second crew warning can now be canceled with a second current E interaction at the ship lever. The prompt changes to **Cancel departure [E]** while the warning is active; another fresh interaction starts a full new warning. Its existing banner shows living crew aboard, living crew total, and crew away. EN/TR/RU use the same numbers and the existing cached DOM update.

This is a bounded cooperation hypothesis: seeing someone still away and being able to reverse a premature departure may produce a clearer rescue-or-leave decision. Frictional's [planning and consequences essay](https://frictionalgames.com/2017-06-choices-consequences-and-the-ability-to-plan/) supports exposing enough information for choices and consequences. It does not establish that this change improves TFG retention or fun. The owner's experience baseline stays **1/10** until observed play supports a different conclusion.

## Native authority and lifecycle

- The native interaction captures a lever receipt: run identity, moon, seed, day, phase, host epoch, dock state, and departure revision. The registered host request validates it before calling module-wrapped `hostLever`, so legacy wrappers that discard extra arguments cannot discard admission. Dock dispatch and planetary landing retain separate receipts even though dispatch stays in orbit.
- Operators must be host or a known native remote with no Session grace-loss record, alive and not downed, standing on actual ship floor, within the native lever reach, and unobstructed under Rapier STATIC/DOOR queries. There is no `noLos` admission or arbitrary route repair. Direct lifecycle callers still require the same physical admission at native `hostLever`.
- Start and cancel increment the native run revision before synchronous Session self delivery. Old requests cannot toggle a later countdown. Each warning owns its captured pending object; cancel/restart invalidates the old timer. Timer ticks also require the original host role and epoch, preventing mutation, broadcast or takeoff after migration.
- Actual `aiPlayers()` derives `inShip` from native positions. The banner uses exactly the native `hostFinishTakeoff` living/aboard predicate: `!dead` and `inShip || inDoorway(pos)`. A living crew member on the doorway sill counts aboard; dead crew are excluded.
- Ship faults delegate pending cancellation and warning expiry, because the warning has already passed preflight. Repaired preflight still starts the warning; expiry cannot roll a second fault event. Voyage finalizes a mission only after accepted native takeoff, so warning start, cancellation and ignored midnight departure cannot fail an active job. Immediate accepted departure retains mission finalization.
- Cargo13 delegates pending cancellation before its departure unload, preserving cargo loaded during the warning. Fresh start and actual departure keep their existing release behavior. The regression loads a native ItemManager item through the actual Cargo13 request, then checks custody, value and IDs across cancel and restart.
- Existing save-load and host-promotion code clears interrupted warning state. No extra cargo, wallet, quota, clock, director, resource, or permanent progression meter is introduced. Root owns the combined protocol bump/publication.

## Verification and limits

The focused native checks use real ship geometry, Rapier floor/range/LOS, the native action selector, real Session self delivery and serialized peer request/receive. A controlled `game.later` clock and certified cockpit starting poses are explicit fixtures; they establish lifecycle behavior, not an earned walk or human play.

Observed RED failures before correction: a second current peer lever request failed to cancel; the actual default fault wrapper created another fault instead of canceling; an active voyage job failed when the warning merely started; the actual HostMig epoch-adoption path let the old warning advance from eight to zero; Cargo13 cancellation changed a native loaded item's holder to null; a grace-lost native Session peer could still start a warning. Each corresponding regression passes after the correction. Negative start and cancel controls cover missing/stale receipts, epoch/revision changes, unknown/disconnected/grace-lost/dead/downed crew, below-floor position, range and actual blocking collider. Cached actions, canceled timers, doorway/death counts and unchanged DOM updates are also checked.

`cycle2_flow`, `cycle3_flow` and `openplaces35_lifecycle` keep their world lifecycle doubles but now give lever admission a real built ship, certified cockpit pose and native Rapier query. `dock37` uses the actual registered host handler and labels its post-dispatch cockpit reset as setup; a cached dispatch receipt cannot become landing. The existing voyage double now explicitly changes phase when its immediate departure is accepted. These fixture changes preserve the guard rather than weakening it.

Final focused command: bundled Node24.19 `tools/harness/run_all.mjs -j 4 extraction39 crew38 power38 dock37 openplaces35_lifecycle cycle2_flow cycle3_flow hostmig voyage cargo13` passed **11/11 in 21 seconds**. Scoped `git diff --check` passed. Root owns the combined build, full suite and browser freeze. Browser Gauntlet results belong in the combined Wave39 evidence, not in this native report.

## Bounded Gauntlet acceptance

With frozen source and one simulation clock, use a fresh silent disposable browser profile and two native crew sessions. Start at a clearly labeled setup location, then use ordinary movement, aim and E with normal floor/range/LOS. Carry the already authorized first-floor return route to the cockpit; do not replace the return with an injected result.

1. With one living crew member away, the lever starts an eight-second warning showing one aboard/two living/one away. The current cockpit prompt offers cancellation.
2. A second new E press cancels before expiry; both peers clear the warning, the ship remains on the moon and its door remains available. Waiting past the abandoned expiry must not start flight. An active job remains active.
3. Bring the second living crew member to the native ship or doorway, observe two aboard/zero away, then start a fresh warning. One completed warning yields one normal takeoff; the job's normal departure outcome resolves then.
4. Preserve a failure trace if either player cannot understand the option, the banner/aim blocks ordinary interaction, or a wrapper launches unexpectedly. Technical success is separate from whether a blind player voluntarily uses cancellation, communicates a rescue decision, or wants another shift. Long-term retention is unmeasured.
