# Wave19 renderer feedback fix

Baseline `33fe646`. Initial source audit covered Engine.render/resize, camera-item photo capture and LandingQueue prewarm. Native feedcams/feedcams2 are game/activity models without GPU targets. That audit missed a fourth producer in **public built-in mods**: enabled-by-default `public/mods/helmet-cameras.js`. The historical warning cannot be assessed by searching `src` alone.

Serialized actual two-peer Chromium startup QA armed the private GL diagnostic before join. A failing main-scene MeshBasicMaterial draw had sampler `map` on unit 0 equal to the framebuffer color attachment. Live scene inspection identified the mesh beneath the ship/tilt group: PlaneGeometry 0.92×0.69, map a render-target texture 160×120. These identities exactly match the native helmet monitor. Its live-feed pass rendered the same scene into `mon.rt` while its own screen sampled `mon.rt.texture`.

The fix hides only that screen while writing its target, restoring its exact previous visibility in the existing finally. Monitor casing, overlay, actual live feed, night vision and update cadence remain intact. Prior target, camera/viewmodel, remote avatar, fog and lighting restoration remain intact. There is no renderer reset, warning filter, shader downgrade or art removal.

`helmet_cameras19.test.mjs` installs the actual shipped built-in mod, drives native netReady/update hooks and inspects real Three scene visibility/material→active-target identity at the feed render boundary. It failed before the patch with a visible self-attachment sampler and passes afterward. It checks the normal restored monitor and a pre-hidden screen/camera/avatar through a deliberate render exception, along with prior target/fog/light restoration and session cleanup. Existing lcmods regression passes.

`render19_probe.mjs` is private bounded QA instrumentation for init scripts. At most 6,000 startup/main draws and four errors are inspected; actual framebuffer/program-sampler identities and native object/material paths are captured. `stop()` restores all prototype and renderer methods. QA stops it in finally even below the cap. Its 10ms owner-attachment poll does not enter product code. Synchronous GL queries consume errors and invalidate FPS timings from this probe. Separate unwrapped warnings and fresh after-patch draws must establish actual browser improvement.

Actual after-patch browser evidence is pending. No universal stutter/FPS cure is claimed. The monitor currently uses ship/distance eligibility rather than main-camera frustum eligibility; narrower visibility culling is a follow-up candidate needing actual looking-away/return proof, not part of this alias correction.

Fresh after-patch actual browser confirmation passed: 24 host and 14 peer native 160×120 bodycam target passes were observed. Both monitor screens and parents were restored visible. Armed actual draw samples covered 4,089 host / 2,883 peer draws with zero GL errors; after restoring all diagnostic hooks, another 3.5 seconds of native unwrapped rendering produced zero feedback warnings. Evidence: `/tmp/tfg-qa19/results.json`, screenshots `07`/`08`. This bounded evidence verifies the identified native bodycam producer on both peers, not all possible future render paths or hardware FPS. No GPU timing comparison is inferred from the diagnostic.
