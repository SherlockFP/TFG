## Concrete feedback defect: pockets erase the carry goal

`Objectives.compute` counts carried sellable items only in `player.slots`.
`OneGoal.carriedValues` uses the same restriction for escape priority and the
camera-tag loss preview. `Guide.holdsScrap` also checks only slots. Native Inventory
stores the same held item IDs in pockets/backpack via `inv.k = 'bag'`; this is the
normal full-hotbar or two-handed pickup route and also an ordinary inventory move.
Stashing the only scrap can therefore remove the carrying/return goal without
removing the cargo. Guide's `!carrying` test can also treat pocket cargo as unloaded.

A focused read-only diagnostic used an actual `WorldItem` held by the local host,
the installed Inventory/OneGoal modules and actual `Objectives.compute`. Inventory
reported the held 31-credit Old Router in `bagItems()`, while `carriedValues()` was
empty and the selected outside goal was `Find the facility entrance (40 m)`.
No carrying line existed. Log: `/tmp/tfg-expedition29-bag-triage.log`.
This is a labelled native held-state fixture, **not** physical pickup or browser
input evidence. This initial audit preceded the approved implementation below.

Proposed narrow correction: enumerate actual local native salvage from hotbar and
`inventory.bagItems()`, deduplicate IDs, and exclude remote/container custody,
bodies, soulbound items and nonsellable tools. Reuse that identity-based count in
Objectives, OneGoal and Guide. Preserve the existing wallet, finite item values,
extraction/drop rules, grace and mystery. Required proof is a real native pickup →
pocket move → return/drop lifecycle, alongside duplicate, remote, body, soulbound
and tagged-preview controls. A pocket move must not award extraction or tutorial
completion, and survival warnings must retain priority.
