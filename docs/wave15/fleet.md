# Fleet first-session clarity — wave 15

The existing fleet chooser now uses the game's wide panel and responsive two-column cards. Each vessel shows its actual purchase price (including a clear free-starter action), saved fitted room names/tiers and relevant current shipyard effects. Quotes derive from `shipyard_core.effects` and `routeMul`, using an owned vessel's current upgrades instead of stock brochure values. Cargo shows sale bonus/rack slots, Recovery shows body-revival cost/rest duration, Survey shows craft-time reduction/observation scan range. Route surcharge uses one decimal where needed (stock Hauler 7.5%). Equipment is explicitly sold separately; no fictional ship preview, gear bundle or fake total equipment cost is advertised. Missing crew credits are shown and unaffordable/selected/client/dead/downed choices are disabled.

Selection and departure are separate physical actions: the chooser displays the selected vessel and tells the host to leave the office and use the departure kiosk. The normal dock objective names the selected vessel and shows walking distance; before selection it directs the host to claim a free ship at the office. Clients see a clear waiting-for-host objective instead of being told to purchase a ship they cannot control. A 14-second existing WorldMarker indicates office, then kiosk when selection changes. It exists only for a living host at the dock, expires without renewing, and is disposed on departure/death/leave. There is no new permanent HUD panel or compass core edit.

Host authority, near-console validation and free re-selection remain. Dead and downed host requests are rejected. Dispatch assigns crew spawn positions using the same stable ID hash as normal Game.spawnInShip, instead of stacking every player at spawn zero. Newly joining clients already receive host fleet/layout state through the generic welcome snapshot and native spawn delegation. Selecting another hull still snapshots current rooms, parts and decoration before restoring that vessel's saved layout. New campaigns preserve owned hull upgrades but start at the dock; resumed campaigns retain saved dock/underway state. The existing shipyard remains responsible for real module geometry, revive pads and bunk respawn behavior.

Files: game/fleet13.js (chooser, objectives, temporary marker, dispatch), game/fleet13_core.js (actual quotes and deterministic spawn index), existing tools/harness/fleet13.test.mjs. No changes to hub/world geometry, game.js or core UI/HUD.

## Loaded cargo when changing hull

A successful change to another hull now relocates loose items from the old module/deck volumes into native permanent-core spawn positions before swapping layouts. Successful boarding also transfers remaining loose module cargo before unloading the dock, covering a room rebuild that has not yet reached the shipyard polling tick. Core cargo keeps its position; held inventory, bag items, grab carriers and deployed ladders are excluded. Ground items below the ship floor (y <= -0.8) and items outside the old owned-room volumes are never pulled aboard. Failed or unchanged purchases do not relocate anything.

Transfer uses existing host-authoritative `it` drop events tagged `f13move`, without remove/spawn IDs. Native drop expects a previously held item and otherwise leaves a loose item's old physics body at its old location, so Fleet installs a narrow tagged-drop ItemManager.onEvent wrapper that removes that old body before the normal native drop/body rebuild on host and peers. Item value, base value, tier, battery, charges, ammo, affix and collected state are untouched. Drop velocity is zero; center height accounts for the item's current world bounding-box height. This is a functional cargo transfer, not a new cargo ownership or duplication mechanic.

The existing fleet harness now uses actual WorldItem construction and ItemManager.onEvent with two item managers and the host drop broadcast. It tests Hauler-to-Courier transfer of the same item object/ID, matching peer transform and rebuilt physics transform, unchanged metadata and item count, failed-purchase no-op, untouched held/core/hub-ground/outside items. It then invokes native hostMethods.hostSave, loadRun and hostMethods.hostInit: moved cargo remains in the core and keeps value/base value/tier/battery/charges/ammo after reload. This exposed a native reload omission: saved `col` was dropped, allowing old cargo to be recorded as newly secured. Root forwards that existing field during restoration and the actual native save/reload regression verifies it. Native reload still assigns fresh item IDs; same-session Fleet transfer preserves both ID and `col`. Physics adapters in this harness validate the native event/body contract, not an extended real-Rapier simulation of a crowded hold; actual browser cargo packing remains QA's responsibility.
